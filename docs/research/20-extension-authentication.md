Last verified: 2026-10-01

## Bottom line

Use the **API Key plugin** (`@better-auth/api-key@1.7.6`), minted by our own Hono route after an in-browser approval page, and verified by our own middleware on a small allow-listed set of routes. It is the only plugin that gives all of: hash-at-rest, per-key list and revoke, per-key permissions, per-key expiry, plaintext returned once, and one new table. The Device Authorization plugin on its own issues a full, unscoped Better Auth session, so it fails "narrow scope". The OAuth Provider route (`oauthProvider` + `oauthDeviceAuthorization` + `jwt`) does give real scopes, but costs a full authorization server (7+ tables, a JWKS, consent screens) and its consent record is per user and client, not per install. The extension should obtain the token with `identity.launchWebAuthFlow` plus a one-time code exchange (PKCE style). `externally_connectable` is not supported in Firefox, and RFC 8628 is designed for devices without a browser. Store the token in `storage.local`, readable only by the service worker and extension pages. Extension requests should carry the token only and no cookies, so they need no credentialed CORS and can go straight to the Worker origin; that departs from ADR-0004 and needs the ADR amended.

### The `usePlural` and Drizzle detail

The Drizzle adapter resolves a Better Auth model to a Drizzle schema key by trying the model name, then `${model}s` when `usePlural` is set (`@better-auth/drizzle-adapter/dist/index.mjs:271-285`). So the schema export must be `apikeys` for model `apikey`, which matches how `users`, `sessions` and `accounts` are already named in `packages/db/src/schema.ts`. Property names must equal the Better Auth field names (same rule as doc 07 §6). Fields of `apikey` (`@better-auth/api-key/dist/index.mjs`, `apiKeySchema`): `id`, `configId` (default `"default"`), `name`, `start`, `referenceId` (owner user id), `prefix`, `key` (hash), `refillInterval`, `refillAmount`, `lastRefillAt`, `enabled` (default true), `rateLimitEnabled`, `rateLimitTimeWindow`, `rateLimitMax`, `requestCount`, `remaining`, `lastRequest`, `expiresAt`, `createdAt`, `updatedAt`, `permissions` (JSON string), `metadata` (JSON string). `referenceId` is `text` in Better Auth; our `users.id` is `uuid`, so either column type works because the check compares names, nullability and defaults only (doc 07 TL;DR 5). `id` is generated by our `advanced.database.generateId`, which returns a UUIDv7 (`apps/api/src/lib/auth.ts`), so the `id` column must be `uuid`.

### Why each plugin does or does not fit

- **bearer**: not a token type. It is a transport for session tokens. Rejected: no scope, plaintext at rest.
- **device-authorization alone**: rejected. The approval flow is sound, but the output is a full session. Anything that accepts a session cookie accepts it. Also the user-code-bound-to-first-viewer behaviour (`routes.mjs:528-545`) means whoever opens `/device?user_code=…` first while signed in becomes the approver; the UI must show what is being authorized, as the docs require ("Production security requirements").
- **api-key**: fits. Gotchas, all from source: (a) the default rate limit of 10 per 24 h would break passive capture; set `rateLimit` explicitly. (b) Every successful verify does at least one UPDATE on the key row (`claimUsageInDatabase`, `index.mjs` after line 1700: guarded `incrementOne` for rate limit when enabled, then an `update` of `updatedAt`). That is one extra DB write per extension request. (c) Leave `enableSessionForAPIKeys` at its default `false`. When true, any valid key header becomes a full mock session on every Better Auth endpoint (`index.mjs:2374-2420`), and the docs warn "This is generally not recommended" (api-key advanced, Sessions from API keys). (d) With `enableSessionForAPIKeys` off, the `x-api-key` hook is inert (`findApiKeyAndConfig` skips configs without it), so our own middleware must call `verifyApiKey`. (e) Keep a single verification per request; the docs warn that `verifyApiKey` followed by `getSession` double-counts.
- **oauthProvider + device grant**: the correct tool if third parties or MCP clients will also need scoped access to this API. For one first-party extension it is more surface than needed (JWKS rotation, client registration, consent pages, DPoP and introspection options). Its consent record is per `(user, client)`, so "list and revoke each install separately" is not a first-class feature. **UNCONFIRMED** that separate installs get separately revocable refresh-token rows through a public endpoint.
- **mcp**: for MCP servers only. Not relevant.
- **jwt alone**: not for authentication per its own docs; no revocation.

## 2. Best fit for this requirement

Requirement: per-install token, narrow scope (create captures, read/write capture settings, list stored items; not read item content, ask, or keys), user lists and revokes devices, plaintext shown once.

Caveats the spec must settle:

1. **Scope is enforced by routes, not by the token.** The plugin only answers "does this key have permission X". The repo's `GET /items` and `GET /items/:id` exist in `apps/api/src/lib/items/routes.ts` (lines 327, 343) and I did not read what they return. "List stored items but not read item content" needs a metadata-only list route that the extension may call; the existing routes must stay session-only. Capture-settings routes do not exist in `apps/api/src/index.ts` yet. UNCONFIRMED what fields `/items` returns.
2. **Permissions are a JSON string** compared with `role(apiKeyPermissions).authorize(required)` (`index.mjs:1670-1680`). Required permissions must be a subset of the key's. Define the resource and action names once, in one module.
3. **Cap the lifetime.** `keyExpiration.maxExpiresIn` defaults to 365 days. The right lifetime is a product and security decision (open decision 2).

**Recommended flow** (OAuth authorization code with PKCE shape, per RFC 8252 for public native-style clients; I did not fetch RFC 7636/8252 themselves, so the PKCE mechanics below are **UNCONFIRMED** against a primary source and should be checked when specifying):

1. Service worker generates a random `code_verifier`, derives `code_challenge`, and calls `launchWebAuthFlow({ url: <web>/extension/authorize?redirect_uri=<getRedirectURL()>&code_challenge=…&device_label=…, interactive: true })`. Only call it from a user gesture; Chrome's docs say interactive flows should be user-initiated.
2. The web page (existing session cookie) shows what is being authorized, requires an explicit Approve, then calls a session-authenticated Hono route that stores a short-lived single-use code bound to `(userId, code_challenge, redirect_uri)` and redirects to `redirect_uri?code=…`. Better Auth's `verifications` table (`internalAdapter.createVerificationValue`, `internal-adapter.mjs:701`) can hold it, or a dedicated table can.
3. The server must validate `redirect_uri` against an exact allowlist of the Chrome and Firefox redirect URLs from config. Never accept arbitrary URIs.
4. `launchWebAuthFlow` resolves with the final URL; the extension reads `code`, then `POST`s `{ code, code_verifier }` to the Worker. The server verifies the challenge, deletes the code, calls `auth.api.createApiKey({ body: { userId, name, permissions, expiresIn, prefix, metadata } })`, and returns `key` once.
5. The extension saves `key` and never shows it.

Why a code exchange rather than returning the key in the redirect URL: the final URL is returned to the extension, but may also pass through browser history and logs; a one-time code with a verifier keeps the long-lived secret off URLs.

Unconfirmed items for this flow: (a) whether the `launchWebAuthFlow` window shares the profile's cookies so an already-signed-in user is not asked to sign in again (neither Chrome nor MDN pages I read state it); if the user is not signed in, the authorize page must run our own sign-in and return. (b) Whether Google sign-in works inside that window. (c) The literal Firefox redirect domain; MDN says only "fixed domain name". Test all three on both browsers before committing to this flow; the content-script handoff in a normal tab is the fallback if (a) or (b) fails.

## 4. Where the token lives in the extension

| Area              | Behaviour                                                                                                                                                                                                                                     | Source                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `storage.local`   | Persists until the extension is removed; Chrome limit 10 MB. MDN: "The storage area is not encrypted and shouldn't be used for storing confidential user information"                                                                         | https://developer.chrome.com/docs/extensions/reference/api/storage; `mdn/content` `api/storage/local/index.md` line 27 |
| `storage.session` | In memory only; cleared when the browser restarts, and in Chrome also when the extension is disabled, reloaded or updated. Not exposed to content scripts by default (`setAccessLevel` changes this). Firefox 115+, Chrome 102+, Safari 16.4+ | Chrome storage page; MDN `storage/session`; BCD `webextensions/api/storage.json`                                       |

Implications and recommendation:

- `storage.session` is safer against disk-resident leaks but forces re-authorization after every browser restart and every extension update. For passive capture that is unacceptable.
- Recommend `storage.local`, read only from the service worker and extension pages, and never handed to a content script (content scripts run inside web pages, and for Chrome and Firefox MV3 they make requests "in context of the page", so a token placed there would also send page-visible requests; MDN Content_scripts, XHR and Fetch). The residual risk (anyone with access to the browser profile can read the token) is bounded by the server side: narrow permissions, per-device revoke, expiry, hashed at rest.
- Whether Chrome exposes `storage.local` to content scripts by default is **UNCONFIRMED** from what I read. The Chrome page states the default only for `session`. Do not rely on it; keep content scripts message-only.
- Do not use `storage.sync`: it syncs across browsers the user is logged into (Chrome storage page), which would copy a per-device token to other devices.

## 5. Hono middleware: session cookie or extension token

Current code (`apps/api/src/lib/request-context.ts`, `apps/api/src/index.ts`): `requestContext` builds `db` and `auth` per request; `requireUser` calls `auth.api.getSession({ headers })` and sets `userId`. Everything after `app.use("*", requireUser)` (`/keys`, `/items`, `/threads`) is session-only.

Recommendation: **default deny**. Do not change `requireUser`. Add a second middleware and mount it only on a separate, narrow router:

```
app.use("*", requireUser)           // unchanged: cookie only
app.route("/keys", ...)             // session only
app.route("/items", ...)            // session only
app.route("/threads", ...)          // session only
```

becomes, in order:

```
app.route("/ext", extensionRoutes)  // mounted BEFORE requireUser; behind requireExtensionToken
app.use("*", requireUser)
...
```

`requireExtensionToken` (sketch of behaviour, not code to copy):

1. Read the key from `Authorization: Bearer <key>` (one header, not two).
2. Call `c.var.auth.api.verifyApiKey({ body: { key, permissions: <required for this route> } })` once. The endpoint is server-only (api-key docs, Verify), so it cannot be reached from a browser.
3. On `valid: false` return the same 401 shape as `requireUser` (`apiError(c, 401, "unauthenticated", …)`). Do not distinguish expired from revoked to the caller.
4. Set `userId` from `key.referenceId`; set `authMethod = "extension-token"`.

Why separate routes rather than "cookie or token" on existing routes: a token-capable `requireUser` would make the token valid on `/keys`, `/threads` and `GET /items/:id` unless every handler also re-checks permissions. Path-level default deny means a new route is session-only until someone deliberately mounts it under `/ext`. Handlers that are shared (for example the capture-create logic behind `POST /items/url`) should be called from both routers rather than exposing the session router.

Also: the Better Auth origin and CSRF check runs only when the request has a `Cookie` header (`apps/api/node_modules/better-auth/dist/api/middlewares/origin-check.mjs:101,108`: `if (!(forceValidate || useCookies)) return`). Extension requests should send no cookies (`credentials: "omit"`), so there is nothing for CSRF to ride on. That is the property that makes the token model safe with a permissive CORS policy (§6).

Management endpoints (list devices, revoke) are session-authenticated and can be the stock `/api/auth/api-key/list` and `/api/auth/api-key/delete`, which the existing `app.on(["GET","POST"], "/api/auth/*", …)` already forwards. The stock `/api/auth/api-key/create` must not be the mint path: client calls cannot set `permissions` (`index.mjs:734`) and a user could mint an unscoped key with the default config. Either do not rely on defaults (set `permissions.defaultPermissions` to the narrow set) or `disabledPaths: ["/api-key/create"]` and mint only through our route; that choice is open decision 3.

## 6. CORS and origin

Facts:

- The Worker today: `cors({ origin: (origin, c) => origin === c.env.WEB_ORIGIN ? origin : null, credentials: true })` on `*` (`apps/api/src/index.ts`). An extension origin gets no `Access-Control-Allow-Origin`.
- Chrome: "A script executing in an extension service worker or foreground tab can talk to remote servers outside of its origin, as long as the extension requests host permissions"; content scripts "are also subject to the same origin policy" (https://developer.chrome.com/docs/extensions/develop/concepts/network-requests).
- Firefox MV3: for content scripts "host permissions don't work in content scripts, but they still do in regular extension pages" (MDN Content_scripts, XHR and Fetch).
- I did not find a primary-source statement of the exact `Origin` header value extension fetches send, nor whether a `chrome-extension://` or `moz-extension://` origin triggers a preflight when host permissions are granted. **UNCONFIRMED.** Also **UNCONFIRMED** from a primary source I fetched: that the `moz-extension://` host is a random per-profile UUID rather than the add-on ID, which would make an exact Firefox origin allowlist impossible.

Recommendation:

1. Declare the API origin in the extension's `host_permissions` and make all requests from the service worker or extension pages, never from content scripts. That alone makes responses readable on both browsers per the docs above.
2. Do not rely on that alone. Add the extension origins to the Worker's CORS policy for `/ext/*` only, with `credentials: false`, `allowHeaders: ["Authorization", "Content-Type"]`, and `origin` matching `chrome-extension://<pinned id>` and any `moz-extension://` origin (prefix match for Firefox if the UUID is random). A permissive origin match is safe on `/ext/*` because no ambient credentials exist there: the route ignores cookies and requires a bearer key.
3. Keep the existing strict `WEB_ORIGIN` policy with `credentials: true` for everything else. Do not add the extension origins to Better Auth `trustedOrigins` (used for cookie-bearing origin checks and redirect validation, `origin-check.mjs:112`); they are not needed for token calls.
4. **Worker origin or Vercel rewrite?** ADR-0004 routes browser traffic through the Vercel rewrite only because the `SameSite=Lax` session cookie does not cross `vercel.app` and `workers.dev`. Extension token calls carry no cookie, so that reason does not apply. Going direct to the Worker also avoids two ADR-0004 consequences: the unconfirmed Vercel proxy body-size and streaming behaviour for uploads, and Fast Data Transfer cost. It also keeps `cf-connecting-ip` accurate for per-IP limits (ADR-0004 notes the header identifies Vercel behind the rewrite). The cost: the extension manifest pins a second origin, which changes if the Worker moves to a custom domain, and ADR-0004's statement "The browser only talks to the web origin" needs a carve-out. Recommend direct-to-Worker for `/ext/*` and for the token exchange, with the approval page and device-management UI staying on the web origin. This needs an ADR-0004 amendment; I did not edit it.
5. The exact `Origin` the browsers send and the preflight behaviour must be checked empirically on Chrome and Firefox before the CORS allowlist is finalised.

## Recommendation

Adopt the API Key plugin at 1.7.6 with a single `extension` configuration: SHA-256 hashing on, `enableSessionForAPIKeys` off, rate limit set explicitly, metadata on, minted only by our own route after an approval page that exchanges a one-time code for the key. Obtain the code with `identity.launchWebAuthFlow` on both Chrome and Firefox (Firefox redirect pinned via `browser_specific_settings` and `getRedirectURL()`), keep the token in `storage.local` for service-worker use only, and serve a separate `/ext/*` router behind a `verifyApiKey` middleware with per-route permissions, so every existing route stays session-only by default. Send extension traffic directly to the Worker with `credentials: omit` and a path-scoped CORS rule, and amend ADR-0004 accordingly. Revisit `oauthProvider` only if a second, third-party client needs scoped access.

4. Which item fields count as "listing" versus "content" for the extension's list route (title, URL, captured-at only?).
